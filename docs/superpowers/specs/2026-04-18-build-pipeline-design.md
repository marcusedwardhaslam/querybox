# Build Pipeline Design

**Date:** 2026-04-18
**Status:** Approved

## Overview

Two GitHub Actions workflows: one for continuous integration on PRs and pushes, one for producing release binaries triggered by semver git tags.

---

## CI Workflow (`ci.yml`)

**Trigger:** Push to `main`, pull requests targeting `main`

**Runner:** `macos-latest` (required for GPUI's macOS system framework dependencies)

**Steps:**
1. Checkout repository
2. Restore cargo cache keyed on `Cargo.lock` hash (registry, git sources, build artifacts)
3. `cargo check` — validates the build without producing a binary
4. `cargo clippy -- -D warnings` — enforces lint cleanliness

Cargo caching is critical: GPUI is a git dependency pulled from `zed-industries/zed` main and has significant compile time.

---

## Release Workflow (`release.yml`)

**Trigger:** Push of tags matching `v*.*.*`

**Runner:** `macos-latest` (matrix-ready for Linux and Windows when support is added)

**Steps:**
1. Checkout repository
2. Restore cargo cache
3. `cargo build --release` — full optimized build
4. Rename binary to `querybox-macos-aarch64`
5. Create GitHub Release using `softprops/action-gh-release`
6. Upload renamed binary as a release asset

The build matrix is structured so adding Linux/Windows is a one-line change — no restructuring required.

**Release notes:** Auto-generated by GitHub from commits since the previous tag.

---

## Versioning

Version is managed manually in `Cargo.toml`. No automated tooling.

### Semver Release Process

1. Decide the new version following semver (`MAJOR.MINOR.PATCH`):
   - `PATCH` — bug fixes, no API/behaviour change
   - `MINOR` — new features, backwards compatible
   - `MAJOR` — breaking changes

2. Update `version` in `Cargo.toml`:
   ```toml
   [package]
   version = "0.2.0"
   ```

3. Commit the version bump:
   ```sh
   git add Cargo.toml
   git commit -m "chore: bump version to v0.2.0"
   ```

4. Create an annotated tag:
   ```sh
   git tag v0.2.0
   ```

5. Push the commit and tag:
   ```sh
   git push origin main
   git push origin v0.2.0
   ```

Pushing the tag triggers the release workflow. The GitHub Release title and tag name will both be `v0.2.0`.

---

## Future Considerations

- **Code signing / notarization** — requires an Apple Developer account; revisit before a public launch to avoid Gatekeeper warnings on first run.
- **Linux / Windows builds** — add rows to the release workflow matrix; no structural changes needed.
- **Automated version bumping** — `cargo-release` or similar tools can automate steps 2–5 if the manual process becomes friction.
